# GDGhost AI 매칭 — 현재 구현 정리 & 테스트 계획

---

## 0. 한 줄 요약

- AI 기능은 **LLM이 아니라 "임베딩(bge-m3) + 점수 공식"**이다.
- 질문과 부원 프로필을 벡터로 바꿔 유사도를 구하고, 규칙 점수와 합쳐 **답할 선배 1~3명을 골라 알림**을 보낸다.
- 로직이 맞게 도는지는 백엔드 테스트로 검증돼 있다. 하지만 **실제 임베딩으로 맞는 선배가 뽑히는지(품질)는 검증된 적이 없다.** AI팀은 이 부분을 맡는다.

## 1. 서비스 개요

GDGoC SMU 동아리 커뮤니티 앱(모바일 웹앱, PWA). 핵심은 **후배가 질문을 올리면 맞는 선배에게 자동으로 전달하는 것**이다.

| 영역 | 기능 |
|---|---|
| 계정 | 초대 코드 가입, 이메일 인증, 로그인, 계정 찾기 |
| 부원/프로필 | 관심 분야, 세부 기술, 경험 태그, 근황, 자기소개 → **AI 매칭 재료** |
| **질문/답변** | 질문 작성(익명 가능, 선배 지목 가능), 답변, 채택 |
| **라우팅** | 답이 안 달린 질문을 맞는 선배에게 알림으로 전달 |
| **선배 찾기** | 고민을 입력하면 맞는 선배 추천 (저장 안 함) |
| 커뮤니티 | 피드, 공지, 이벤트/인증, 일정, 소모임 모집, 커피챗, 공유 |
| 운영 | 신고, 운영진 대시보드, 어드민(에러/배치/AI 로그, 라우팅 CSV) |

질문 분류는 5개다: `JOB` 취업·채용 / `CAREER` 커리어·이직 / `PATH` 진로 고민 / `CAMPUS` 학교생활 / `STUDY` 기술·공부

스택: Spring Boot 4 · Java 21 · MySQL 8.4 (서버), React · Vite · TypeScript (웹)

## 2. AI 기능 구조

```
[글 → 벡터]  embedding 패키지                      [벡터 → 선배 순위]  routing 패키지

질문 작성/수정 ─┐                                    10분 배치 / 선배 찾기 API
프로필 변경 ────┼─▶ 텍스트 조립 ─▶ bge-m3 ─▶ DB 저장 ──▶ 점수 계산 ─▶ 상위 3명 ─▶ 알림
재시도 배치(10분)┘   (TextBuilder)  (Workers AI)          (CandidateScorer)
```

### 2-1. 코드 위치

| 파일 | 역할 | 담당 |
|---|---|---|
| `embedding/DefaultTextBuilder.java` | 임베딩에 넣을 텍스트 조립 | **AI팀** ("자리는 백엔드, 조립 규칙은 AI팀") |
| `resources/application.yaml` → `matching:` | 점수 가중치, 컷, 인원 | **AI팀** ("AI팀이 조정한다. 값을 바꾸면 version을 올린다") |
| `routing/CandidateScorer.java` | 점수 공식 (DB와 무관한 순수 계산) | 백엔드 (공식 변경 시 협의) |
| `embedding/WorkersAiEmbeddingClient.java` | Workers AI 호출 | 백엔드 |
| `embedding/EmbeddingService.java`, `EmbeddingRetryJob.java` | 벡터 계산·저장·재시도 | 백엔드 |
| `routing/RoutingCandidateService.java` | 후보 풀 구성 + 점수 계산 호출 | 백엔드 |
| `routing/RoutingJob.java`, `RoutingDelivery.java` | 발송 배치, 알림 | 백엔드 |
| `routing/SeniorMatchService.java` | 선배 찾기 | 백엔드 |

### 2-2. 임베딩

- **모델:** Cloudflare Workers AI `@cf/baai/bge-m3` (다국어, 1024차원)
- **호출:** 타임아웃 3초, 실패 시 1회 재시도. 400/413(글 자체 문제)은 재시도하지 않는다. 긴 글은 모델 한도에서 자른다(`truncate_inputs`).
- **계산 시점:** 질문 작성·수정, 프로필 변경 시 이벤트로 즉시 계산한다. 실패하거나 빠진 것은 10분마다 도는 재시도 배치가 채운다.
- **저장:**
  - `question_embedding (question_id, vector JSON, model)`
  - `member_embedding (member_id, vector JSON, model, source_hash)`: 조립한 텍스트의 SHA-256. 내용이 같으면 다시 호출하지 않는다.
- **로그:** `ai_log (kind, target_id, model, latency_ms, state)`. 글 내용은 남기지 않는다.
  - kind: `EMBED_QUESTION` / `EMBED_MEMBER` / `FIND_SENIOR`
  - state: `SUCCESS` / `FAILED` / `FALLBACK`
- **장애 시:** 예외를 던지지 않고 **규칙 점수만으로 대체**한다. AI가 죽어도 서비스는 돌아간다.

### 2-3. 실제로 임베딩되는 것

벡터는 3종류다. 저장되는 것은 질문과 부원 2종류뿐이다.

#### ① 질문 벡터 → `question_embedding`

| 들어가는 것 | 제한 |
|---|---|
| 분류명 (예: `취업·채용`) | 5개 중 1개, 필수 |
| 제목 | 2~80자, 필수 |
| 본문 | 0~3000자, 없어도 됨 |

```
취업·채용 백엔드 신입 포트폴리오 어떻게 준비하나요?
스프링 공부 중인데 어떤 프로젝트를 해야 할지 모르겠어요
```

- **계산 시점:** 질문 작성 시. 분류·제목·본문 중 하나라도 바뀌면 기존 벡터를 지우고 다시 계산한다.
- **들어가지 않는 것:** 질문자 정보 전부(익명 여부, 학과, 기수 등), 답변 내용

#### ② 부원 벡터 → `member_embedding`

| 줄 | 들어가는 것 | 제한 |
|---|---|---|
| `관심 분야:` | 관심 분야 + 세부 기술(괄호 안) | 관심 분야 **1~4개 필수** (9개 중), 세부 기술은 분야당 0~3개 (56개 중) |
| `경험:` | 경험 태그 | 0~6개 (18개 중) |
| `근황:` | 상태 메시지 | 0~60자 |
| `소개:` | 자기소개 | 0~120자 |

```
관심 분야: 백엔드(Spring, DB 설계), 클라우드(AWS)
경험: 인턴, 해커톤
근황: 백엔드 인턴 끝나고 취준 중
소개: 신입 백엔드 취업 준비 과정을 이야기해 드려요
```

- 비어 있는 줄은 뺀다. 관심 분야가 필수라서 **모든 부원이 최소 1줄은 갖고 있고, 벡터도 항상 만들어진다.**
- 태그는 사용자가 고른 순서가 아니라 시스템이 정한 순서(`sort_order`)로 나열된다.
- **계산 시점:** 가입 완료, 프로필 수정, 10분 배치. 텍스트 해시가 같으면 다시 호출하지 않는다.
- **들어가지 않는 것:** 이름, 닉네임, 학과, 포지션, 기수, 재학/졸업 상태, 연락처, 커피챗 메모, **작성한 답변 글**
  - 학과, 포지션, 기수, 재학/졸업 상태는 규칙 점수(rule)에서 따로 쓴다.

#### ③ 선배 찾기 입력 → 저장하지 않음

| 들어가는 것 | 제한 |
|---|---|
| 분류명 | 필수 |
| 고른 관심 분야명 | 필수 (세부 기술은 안 들어감) |
| 입력 글 | 10~120자 |

```
진로 고민 데이터·AI
대학원을 갈지 바로 취업할지 고민이에요
```

#### 어떤 벡터끼리 비교하나

| 점수 | 비교 대상 |
|---|---|
| profile (라우팅) | ① 질문 ↔ ② 부원 |
| profile (선배 찾기) | ③ 선배 찾기 입력 ↔ ② 부원 |
| history | ① 지금 질문 ↔ ① **그 부원이 과거에 답한 질문** (답변 글이 아니라 질문의 벡터) |

#### AI팀이 볼 만한 특징

- **길이가 비대칭이다:** 질문은 최대 약 3000자, 부원은 태그 나열과 짧은 글 합쳐 약 250자 이내다.
- **형식이 다르다:** 질문은 문장이고 앞에 분류명이 붙는다. 부원은 `라벨: 키워드, 키워드` 형식의 목록이다.
- **부원 텍스트는 사실상 태그가 대부분이다.** 근황과 소개를 비워 둔 부원은 고정 태그 목록 조합이라서 서로 비슷한 벡터가 나오기 쉽다.
- **경험 태그 `대외활동`은 어느 분류의 경험 매핑에도 없다.** 임베딩에는 들어가지만 rule 점수(+0.6)는 받지 못한다.
- **답변 글 자체는 임베딩되지 않는다.** "이 사람이 무엇에 대해 잘 답하는가"는 과거에 답한 질문의 벡터로만 간접 반영된다.

### 2-4. 점수 공식 (`CandidateScorer`)

```
relevance (관련도) = 0.4 × rule + 0.3 × profile + 0.3 × history
total (최종 점수)  = relevance + activity
```

| 항목 | 계산 | 범위 |
|---|---|---|
| **rule** | 아래 규칙 합산, 최대 1 | 0~1 |
| **profile** | `cos(질문 벡터, 부원 벡터)`, 음수면 0 | 0~1 |
| **history** | 그 부원이 답한 과거 질문 중 지금 질문과 가장 비슷한 것의 cos. 채택된 답이면 +0.1. 최대 1 | 0~1 |
| **activity** | `min(답변 수, 10) × 0.01` + (최근 30일 접속 시 0.05) − `넘기기 횟수 × 0.05` | **순위에만 사용** |

**rule 세부**

| 조건 | 점수 | 표시되는 사유 |
|---|---|---|
| 질문 분류에 맞는 경험 태그 보유 | +0.6 | "경험: 인턴" |
| (선배 찾기) 고른 관심 분야 보유 | +0.3 | "백엔드 · Spring" |
| 질문자와 같은 학과 | +0.2 | "같은 학과" |
| 질문자와 같은 포지션 | +0.1 | "같은 포지션" |
| 질문자보다 선배 (기수가 빠르거나 졸업) | +0.1 | (없음) |

학과·포지션·선배 규칙은 **익명 질문에서는 적용하지 않는다** (질문자가 특정될 수 있어서).

**분류별 경험 태그 매핑**

| 분류 | 인정 경험 |
|---|---|
| JOB | 인턴, 정규직 취업, 공모전 수상, 해커톤, 자격증 |
| CAREER | 정규직 취업, 이직, 창업, 프리랜서·외주 |
| PATH | 대학원 진학, 학부연구생, 휴학, 군 복무, 교환학생, 창업 |
| CAMPUS | 복수·부전공, 교환학생, 편입, 휴학, 동아리 운영진, 학부연구생 |
| STUDY | 오픈소스 기여, 해커톤, 공모전 수상, 학부연구생 |

**선정 규칙**

- `relevance ≥ 0.15`(min-score)인 사람만 후보가 된다. activity는 빼고 판단한다.
- 후보를 `total` 내림차순으로 정렬해 **최대 3명**을 고른다.
- 그 외 사유: history ≥ 0.6이면 "비슷한 질문에 답한 적 있음". 다른 사유가 하나도 없고 profile > 0이면 "프로필이 질문과 비슷함".

**점수 예시**

| 상황 | 계산 | relevance | 결과 |
|---|---|---|---|
| 경험 태그 매칭 + cos 0.6 | 0.4×0.6 + 0.3×0.6 | 0.42 | 후보 |
| 태그 없음 + cos 0.5 | 0.3×0.5 | 0.15 | **겨우 후보** |
| 태그 없음 + cos 0.45 | 0.3×0.45 | 0.135 | 탈락 |

→ **규칙 점수가 0인 사람은 유사도 0.5가 사실상의 컷**이다.

### 2-5. 전달 흐름

배치는 10분마다 돈다. 22~08시에는 쉬고, 그사이 쌓인 것은 08시 회차가 보낸다.

1. **지목:** 질문 작성 시 선배를 지목하면 즉시 알림(밤이면 08시). 24시간 반응이 없으면 일반 라우팅으로 넘어간다.
2. **작성 후 1시간 미답변:** 운영진 디스코드 채널에 알림.
3. **작성 후 3시간 미답변:** 점수 계산 → 상위 3명에게 앱 알림.
4. **넘기기:** 넘긴 만큼만 다음 후보로 보충한다. 질문당 최대 5명. 무응답이면 더 보내지 않는다.
5. **3일 경과:** 운영진 요약 대상으로 넘어간다.

**제약:**
- 1인당 하루 3건까지만 받는다.
- 직전 질문을 받은 사람에게 연달아 보내지 않는다.
- 질문 받기를 끈 사람, 목록에서 숨김 처리된 사람, 탈퇴·정지된 사람, 작성자 본인은 제외한다.

**선배 찾기**(`POST /api/v1/senior-matches`): 같은 공식을 쓰지만 알림을 보내지 않으므로 하루 3건 제한은 보지 않는다. 분당 5회 제한이 있다.

## 3. 현재 테스트 현황

| 종류 | 테스트 | 상태 |
|---|---|---|
| 단위 | `CandidateScorerTest` (8), `DefaultTextBuilderTest` (3), `WorkersAiEmbeddingClientTest` (7), `EmbeddingConfigTest` (2) | ✅ 20/20 통과 (11/08 로컬 실행) |
| 통합 | `EmbeddingIntegrationTest`, `RoutingIntegrationTest`, `RoutingApiIntegrationTest` 등 약 50개 | ⏸ Docker 필요 (Testcontainers), 아직 미실행 |
| 실제 API | `EmbeddingLiveTest` (`LIVE_EMBEDDING=true`일 때만 실행) | ⏸ Docker 필요 |
| Workers AI 키 | curl로 직접 호출 | ✅ 정상 (1024차원) |

**한계:** 통합 테스트는 `FakeEmbeddingClient`를 쓴다. 이 가짜 클라이언트는 모든 글에 같은 벡터(전부 0.5)를 돌려주므로 **유사도가 항상 1**이다. 따라서 기존 테스트는 "공식대로 계산되는가"만 검증하고, **"실제로 맞는 선배가 뽑히는가"는 검증하지 않는다.**

**사전 측정 (11/08, 실제 bge-m3)**

| 비교 | cos |
|---|---|
| 백엔드 취업 질문 ↔ 백엔드·인턴 선배 | 0.610 |
| 백엔드 취업 질문 ↔ 디자인·교환학생 선배 | 0.413 |

**설계 문서의 실측 (2026-10-31, 백엔드)**: 맞는 짝 0.53~0.68 · 틀린 짝 0.33~0.53. 이력이 없는 초반에는 profile만으로 relevance가 최대 약 0.2. 표본이 작아 참고용이다.

맞는 짝과 틀린 짝의 범위가 0.53에서 맞닿아 있고, 컷(cos 0.5)이 틀린 짝 범위 안에 있다. **애매한 짝**(같은 개발 분야지만 주제가 다른 경우 등)이 0.5를 넘는지가 핵심 검증 포인트다.

## 4. 테스트 계획

### 4-1. 목표

1. 현재 설정(`2026-10-v1`)으로 **맞는 선배가 상위 3명 안에 드는지** 수치로 확인한다.

### 4-2. 단계별 계획

#### 2단계 — 오프라인 평가셋으로 품질 측정 (핵심)

서버를 띄우지 않고 Python으로 같은 공식을 재현해 측정한다. 서버 저장소 밖에 별도 폴더를 둔다.

```
ai-eval/
├─ .venv/                 # Python 가상환경
├─ data/
│  ├─ members.jsonl       # 가상 부원 10~15명: 관심분야/기술/경험/근황/소개 + 학과/포지션/기수
│  ├─ questions.jsonl     # 가상 질문 20~30개: 분류/제목/본문/익명 여부/작성자
│  └─ labels.csv          # 질문 × 부원 정답표: 2=정답, 1=애매, 0=무관
├─ embed.py               # Workers AI 호출 + 결과 캐시 (무료 한도 절약)
├─ text_builder.py        # DefaultTextBuilder 재현 (변형 실험용)
├─ scorer.py              # CandidateScorer 재현 (application.yaml 값 사용)
├─ evaluate.py            # 지표 계산 + 리포트
└─ results/
```

**평가셋 작성 원칙**

- 5개 분류를 고르게 섞는다 (분류당 4~6개).
- 일부러 **헷갈리는 짝**을 넣는다: 같은 개발 분야지만 주제가 다른 경우, 경험 태그는 맞지만 관심 분야가 다른 경우 등.
- 프로필이 **비어 있거나 짧은 부원**도 넣는다 (가입 직후 신입).
- 익명 질문도 포함한다 (규칙 점수 일부가 빠지는 경우).
- 라벨은 2명 이상이 따로 달고 맞춰 본다.

**측정 지표**

| 지표 | 의미 | 목표 (제안) |
|---|---|---|
| 라벨별 cos 분포 (정답/애매/무관) | 유사도만으로 구분되는가 | 정답과 무관의 분포가 겹치지 않음 |
| 무관 짝의 컷 통과율 | relevance ≥ 0.15인 무관 짝의 비율 | ≤ 10% |
| **Hit@3** | 정답 선배가 상위 3명 안에 1명 이상 있는 질문의 비율 | ≥ 80% |
| Precision@3 | 상위 3명 중 정답의 비율 | 참고용 |
| 후보 0명 질문의 비율 | 아무에게도 안 가는 질문 | 낮을수록 좋음 |

> `scorer.py`가 Java 공식과 같은지는 `CandidateScorerTest`의 입력과 기대값으로 먼저 확인한다.

#### 3단계 — 튜닝 실험

2단계 결과를 기준선으로 두고 한 번에 하나씩 바꿔 비교한다.

| 실험 | 바꿔 볼 것 |
|---|---|
| A. 기준선 | 현재 설정 그대로 |
| B. 텍스트 조립 | 질문에서 분류명 빼기 / 부원 텍스트에 항목 순서 바꾸기 / 소개를 앞으로 |
| C. 컷 | min-score 0.12 / 0.15 / 0.18 / 0.20 |
| D. 가중치 | rule : profile : history 비율 조정 |

- 결과가 좋은 조합만 `application.yaml`에 반영하고 **`matching.version`을 올린다**.
- TextBuilder를 바꾸면 기존 벡터가 낡게 된다. 재계산 방식은 백엔드 팀과 협의한다. 질문 벡터는 수정 시 지우고 다시 만드는 구조이고, 부원 벡터는 해시가 바뀌면 배치가 재계산한다.

#### 4단계 — 실제 서버에서 확인 (Docker 설치 후)

- 로컬 서버에 실제 키를 넣고 띄운 뒤, Swagger에서 **선배 찾기 API**로 평가셋 질문 몇 개를 직접 넣어 본다. 기다릴 필요 없이 바로 결과와 사유가 나온다.
- `ai_log`에서 성공률과 지연시간을 확인한다 (타임아웃 3초 안인지).

#### 5단계 — 출시 후 모니터링 기준 마련

- `routing.csv`로 **보낸 질문 중 답변 비율**과 **넘기기 비율**을 `rank_no`별, `version`별로 집계하는 스크립트를 미리 만든다.
- `ai-logs`의 FALLBACK 비율과 평균 지연시간을 주 단위로 확인한다.
- 설계 문서의 목표치:

| 지표 | 계산 | 목표 |
|---|---|---|
| 라우팅 전환율 | 부원 알림 중 답변 비율 | 50% 이상 |
| 넘김 비율 | 알림 중 넘기기 비율 | 30% 이하 |
| 대체 처리 비율 | `ai_log` 중 FALLBACK 비율 | 5% 이하 |
| 항목별 기여 | 결과와 rule · profile · history의 관계 | 가중치 조정 근거 |

가중치는 학기당 1회 재설정한다.

## 5. 미리 봐 둔 위험 요소

| # | 내용 | 확인 방법 |
|---|---|---|
| 1 | **컷 여유가 작다.** 규칙 점수 0인 사람은 cos 0.5에서 갈린다. 설계 문서 실측에서 **틀린 짝이 0.33~0.53**이라, 틀린 짝 일부가 이미 컷을 넘는 구간이다 (설계 문서도 "표본 작음, 참고용"이라고 밝힘) | 2단계 무관 짝 컷 통과율 |
| 2 | **"프로필이 질문과 비슷함" 사유가 너무 쉽게 붙는다.** 다른 사유가 없으면 profile > 0이기만 해도 붙는다 (cos 0.1이어도) | 평가셋 결과에서 사유를 보고 어색한지 판단 → 기준값 도입을 제안할지 결정 |
| 3 | **출시 초기엔 history가 0이다.** 과거 답변이 없어서 rule과 profile만으로 결정된다 | 기준선 측정 시 history=0으로 둔다 |
| 4 | **관심 분야만 있는 부원은 텍스트가 한 줄이다** (예: `관심 분야: 백엔드`). 같은 분야만 고른 부원끼리는 벡터가 같아 구분되지 않고, 질문과의 유사도가 낮게 나올 수 있다 | 평가셋에 최소 프로필 부원 포함 · 프로필 작성 유도는 기획에 공유 |
| 5 | **익명 질문은 rule이 경험 태그뿐이다.** 임베딩에 더 의존한다 | 익명 질문만 따로 Hit@3 계산 |
| 6 | **질문 텍스트와 부원 텍스트 형식이 다르다.** 질문은 "분류명 제목 본문", 부원은 "관심 분야: … / 경험: …" | 실험 B |
| 7 | **넘기기 감점이 기간 제한 없이 누적된다** (1회 −0.05) | 출시 후 모니터링 |
